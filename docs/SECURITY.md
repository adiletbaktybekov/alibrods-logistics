# AliBros Logistics — Руководство по безопасности (Phase 1)

## 1. Архитектура безопасности

Безопасность платформы AliBros Logistics базируется на принципе **нулевого доверия к клиенту (Zero Trust)**:
- Любые данные, передаваемые клиентом (роли, ID пользователя, токены, Telegram WebApp данные), считаются потенциально скомпрометированными и валидируются исключительно на сервере.
- Доступ к каждому объекту и ресурсу строго проверяется с учётом контекста безопасности вызывающего субъекта.

---

## 2. Ролевая модель доступа (RBAC)

В системе определены 6 ролей с гранулярными правами:

| Роль | Назначение | Права доступа |
| :--- | :--- | :--- |
| `SUPER_ADMIN` | Главный администратор системы | Полный доступ ко всем ресурсам, управлению ролями, аудит-логам и интеграциям. |
| `ADMIN` | Системный администратор | Управление пользователями, складами, отчётами, аудит-логами и заказами. |
| `MANAGER` | Операционный менеджер / логист | Управление жизненным циклом заказов, назначение водителей, просмотр клиентов и складов. |
| `ACCOUNTANT` | Бухгалтер / финансист | Доступ на чтение ко всем заказам, финансовые отчёты, выгрузка данных. |
| `DRIVER` | Водитель-экспедитор | Доступ **только** к назначенным ему заказам, смене их статуса и прикреплению фотоотчётов. |
| `CLIENT` | Селлер маркетплейсов | Доступ **только** к собственным заказам, своему профилю и справочнику складов. |

Все проверки выполняются серверными функциями `requireRole`, `requirePermission` и `assertOrderAccess` (`server/guards.ts`). Роль пользователя извлекается из проверенной криптографической подписи JWT.

## 3. Защита от IDOR (Insecure Direct Object References)

Уязвимость IDOR исключена на уровне доменных сервисов:
```typescript
// Пример из server/guards.ts
export function assertOrderAccess(
  user: AuthenticatedUser,
  order: { clientId: string; assignments?: { driver: { userId: string } }[] }
): void {
  if (['SUPER_ADMIN', 'ADMIN', 'MANAGER', 'ACCOUNTANT'].includes(user.role)) return;

  if (user.role === 'CLIENT') {
    if (order.clientId !== user.id) {
      throw new ForbiddenError('Clients can only view and manage their own orders');
    }
    return;
  }

  if (user.role === 'DRIVER') {
    const isAssigned = order.assignments?.some((a) => a.driver.userId === user.id);
    if (!isAssigned) {
      throw new ForbiddenError('Drivers can only access orders explicitly assigned to them');
    }
    return;
  }

  throw new ForbiddenError('Access to order denied');
}
```

Клиент не может получить доступ к чужому заказу, даже зная его UUID или номер `orderNumber`.

## 4. Хеширование паролей: Argon2id

Пароли пользователей хешируются с использованием современного алгоритма **Argon2id** (победитель Password Hashing Competition, стандарт OWASP):
- **Тип**: `argon2id` (гибридная защита от атак по побочным каналам и параллельного GPU-перебора).
- **Память (Memory Cost)**: 64 МБ (65536 КБ).
- **Итерации (Time Cost)**: 3.
- **Параллелизм**: 4 потока.
- Минимальная длина пароля: **8 символов**.
- Исходный пароль никогда не сохраняется в открытом виде и не передаётся в логгеры.

## 5. Аутентификация Telegram Mini App (HMAC-SHA256)

При входе селлера через Telegram Mini App клиентский скрипт передаёт строку `initData`.
Сервер **обязан** проверить подлинность данных по официальному алгоритму Telegram (`lib/security/telegram.ts`):
1. Парсинг параметров и извлечение параметра `hash`.
2. Алфавитная сортировка оставшихся пар `key=value` через `\n`.
3. Вычисление секретного ключа: `secret_key = HMAC_SHA256("WebAppData", bot_token)`.
4. Вычисление контрольного хеша: `calc_hash = HMAC_SHA256(secret_key, data_check_string).hex()`.
5. Сравнение с защитой от атак по времени через `crypto.timingSafeEqual`.
6. Проверка срока жизни `auth_date` (отклоняются данные старше 24 часов).

**Важно**: Сервер никогда не доверяет `telegram_id` или username, переданным в теле обычного JSON-запроса без валидного `initData`.

## 6. Валидация входных данных (Zod)

- Все входные DTO проходят строгую типизированную валидацию через библиотеки Zod.
- Автоматически отсекаются лишние поля, предотвращая атаки типа Mass Assignment и Prototype Pollution.
- Форматы телефонов, email, ИНН и UUID проверяются регулярными выражениями и встроенными валидаторами.

---

## 7. Защита от DoS и Brute-Force (Rate Limiting)

- Встроенный механизм скользящего окна (`lib/security/rate-limit.ts`) ограничивает количество запросов с одного IP-адреса или токена.
- По умолчанию: максимум 100 запросов в минуту на эндпоинт.
- При превышении выбрасывается `429 Too Many Requests`.

---

## 8. Неизменяемый журнал аудита (`AuditLog`)

Каждое значимое действие в системе автоматически регистрируется в таблице `audit_logs`:
- Вход в систему (`LOGIN`).
- Создание заявки (`CREATE`).
- Смена статуса заказа (`STATUS_CHANGE`).
- Назначение водителя на рейс (`ASSIGNMENT_CHANGE`).
- Изменение прав или ролей пользователей (`ROLE_CHANGE`).

Запись фиксирует `userId`, IP-адрес, User-Agent, старое и новое значения в формате JSON. Записи аудита защищены от модификации или удаления через API.
